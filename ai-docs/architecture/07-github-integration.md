# GitHub Integration

## Integration Modes

### SaaS Mode

Uses one shared ReviewRouter-owned GitHub App.

Flow:

```text
1. User signs in with GitHub OAuth.
2. User installs ReviewRouter GitHub App on org/repos.
3. GitHub sends installation webhook.
4. ReviewRouter syncs installations and repositories.
5. User selects repository in dashboard.
6. ReviewRouter creates setup PR with workflow/config.
7. Customer merges setup PR.
8. Pull requests trigger customer CI review workflow.
```

### Open-Source Self-Managed Mode

Uses curl installer and optionally user-owned GitHub App.

This remains valuable for users who do not want SaaS. SaaS should be simpler and use the shared app.

## OAuth vs GitHub App

GitHub OAuth:

- authenticates dashboard user
- reads user/org access where needed
- maps user to workspace membership

GitHub App:

- owns repository installation
- receives webhooks
- creates workflow setup/update PRs
- posts comments/status if SaaS ever needs direct GitHub operations

## Webhooks

Required webhook handling:

```text
installation
installation_repositories
repository
pull_request
workflow_run optional later
check_run/check_suite optional later
```

Webhook rules:

- verify signature
- store delivery id before processing
- dedupe by delivery id
- enqueue work
- return quickly

## Workflow Provisioning

Default behavior:

- create branch: `reviewrouter/setup` or deterministic update branch
- write `.github/workflows/reviewrouter.yml`
- optionally write `.reviewrouter/config.yml` later if needed
- create pull request
- do not push directly to main

Provisioning auth:

```text
Default v1 SaaS mode:
  GitHub App creates setup/update PR
  requires contents:write, workflows:write, pull_requests:write

Fallback self-managed mode:
  curl installer uses the user's local gh/git auth
  useful when an organization does not approve the SaaS App permissions
```

A real spike confirmed that a lower-permission App cannot write workflow files. GitHub requires workflow write capability for `.github/workflows/*` changes. We accept that permission cost to make SaaS onboarding one-click, but still create PRs only and never push directly to the default branch.


Workflow should reference selected action version:

```text
stable - UI choice resolved by dashboard to explicit vetted release tag
release - pinned release tag selected by user
main - live main branch for fast updates
```

SaaS dashboard should support update PRs when desired version changes.

## GitHub App Permissions

Use least privilege and explain permissions in UI.

Likely v1 App permissions:

```text
metadata: read
contents: write
workflows: write
pull_requests: write
issues: write
actions: write
```

Why each write permission exists:

```text
contents: write      create setup/update branch commits
workflows: write     modify .github/workflows/reviewrouter.yml
pull_requests: write open setup/update PRs and post review state
issues: write        PR issue comments and bot summary comments
actions: write       rerun review workflow after /rr skip when needed
```

The UI must explain that `workflows: write` is for ReviewRouter setup/update PRs, not for reading or running customer code in SaaS.

## Status and Comments

Review comments are generated by ReviewRouter Action running in customer CI.

Depending on workflow token setup:

- comments can come from GitHub App bot if workflow mints App installation token
- or from `github-actions[bot]` if using default GitHub token

SaaS should clearly explain the difference:

```text
GitHub App bot: cleaner identity and audit, needs app token wiring
GitHub Actions bot: simpler setup, generic identity
```


## Action Runtime Config Through OIDC

Generated workflows should include `id-token: write` so ReviewRouter Action can request a GitHub Actions OIDC token.

The action uses that token to fetch SaaS-managed runtime config and optionally report health metadata. This avoids long-lived ReviewRouter API tokens in customer repositories.

If OIDC fails, the action should fall back to static workflow config where possible.

## Provider Secrets

For v1, SaaS guides setup but does not store secrets.

Recommended:

- org selected-repo secrets for teams
- repo secrets for single repo setup
- self-hosted runner persistent `CODEX_HOME` for long-lived Codex OAuth refresh behavior

## Failure Handling

Common failures to surface clearly:

- App not installed on repo
- insufficient GitHub permissions
- workflow missing
- workflow installed on wrong branch
- provider secret missing
- Codex auth stale or invalid
- fork PR skipped because secrets unavailable
- setup PR already exists
- branch protection blocks workflow PR merge
