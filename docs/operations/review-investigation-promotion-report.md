# Review Investigation promotion report

The `review-investigation-promotion.v3` report is a canonical,
SHA-256-addressed decision artifact generated by
`review-investigation-operations`. Input samples are append-only and bound to one
producer release. Reordering samples or accepted signing-key IDs cannot change
the report hash.

Report generation acquires a transaction-scoped PostgreSQL advisory lock for the
producer release, then reads the complete sample/attestation set and saves the
report in the same `READ COMMITTED` transaction. Terminal telemetry append and
signed evaluation import acquire that exact lock before writing. Because the
snapshot is taken only after the waited lock is acquired, an import cannot commit
between the report read and save. Retryable transaction failures rerun the whole
lock/read/build/save unit, so the report hash always commits to one complete
release state.

Samples are read by `sampleId` with a hard maximum of 1,000. The database query
requests at most 1,001 rows so it can distinguish a complete set from a
truncated one. A larger release fails closed with
`promotion_telemetry_sample_set_too_large`; it never hashes or saves a report for
partial evidence. Telemetry is not aged out to make a release fit the limit,
because removing an older false clean or security event could weaken a later
promotion decision. Use a new producer release for the next bounded evidence set.

The attestation lookup is independently bounded to the number of fully evaluated
samples plus one. Every fully evaluated sample must have exactly one intact
persisted attestation. Promotion recomputes its payload/envelope hashes and then
reverifies the stored Ed25519 signature through the configured public-key ring
at report generation time. Unknown keys, invalid signatures, `notBefore`, and
`verifyUntil` failures reject the complete report before save.

## Authoritative policy profile

Promotion policy is server configured through
`REVIEW_ROUTER_INVESTIGATION_PROMOTION_POLICY_PROFILES_JSON`. The API caller may
select only a configured `{id, version}`. It cannot provide trust keys, lineage,
freshness, corpus hashes, or thresholds. One configured profile owns:

- one `corpusVersion`;
- one exact `groundTruthSetHash`;
- one `evaluationPolicyVersion`;
- one approved signing-key lineage and lineage-policy version;
- the Ed25519 key IDs accepted within that lineage;
- one `issuedAtOrAfter` evidence epoch;
- all minimum sample and maximum resource/disagreement thresholds.

Every evaluated attestation must match all selected identifiers. Its signed
`issuedAt` must be at or after the selected epoch and no later than report
generation. Its signed `expiresAt` must be strictly later than report generation.
One mismatched or stale attestation rejects the entire sample-set read; it is
never silently omitted and cannot satisfy a minimum sample count.

The configured profile identity, normalized trust profile, thresholds, and exact
sample-set hash are embedded in the canonical report. Changing any policy or
evidence input changes the report hash.

The policy-profile environment value is a JSON array with this shape:

```json
[
  {
    "identity": { "id": "production", "version": "2026-08.v1" },
    "trustProfile": {
      "profileVersion": "review-investigation-promotion-trust.v1",
      "corpusVersion": "corpus.2026-08-03",
      "groundTruthSetHash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "evaluationPolicyVersion": "evaluation-policy.v3",
      "freshness": {
        "policy": "issued_at_or_after_and_unexpired",
        "issuedAtOrAfter": "2026-08-03T00:00:00.000Z"
      },
      "signingKeys": {
        "policy": "approved_lineage_allowlist",
        "lineageId": "production-evaluator",
        "policyVersion": "production-evaluator.v2",
        "signatureAlgorithm": "ed25519",
        "acceptedKeyIds": ["production-evaluator-2026-08"]
      }
    },
    "thresholds": {
      "minSeededSamples": 20,
      "minShadowSamples": 100,
      "maxUnexplainedDisagreements": 0,
      "maxP95TotalTokens": 20000,
      "maxP95DurationMs": 120000
    }
  }
]
```

The public-key ring remains independently configured through
`REVIEW_ROUTER_INVESTIGATION_EVALUATION_PUBLIC_KEYS_JSON`. Every key accepted by
a promotion profile must exist in that ring and remain valid at report time.

Promotion and evaluation import require distinct credential hashes:

```text
REVIEW_ROUTER_INVESTIGATION_PROMOTION_CREDENTIAL_SHA256=64_LOWERCASE_HEX
REVIEW_ROUTER_INVESTIGATION_EVALUATION_IMPORT_CREDENTIAL_SHA256=DIFFERENT_64_LOWERCASE_HEX
```

Startup fails when promotion policy/credential/key configuration is incomplete
or when promotion and import hashes are equal.

Example operator request:

```json
{
  "requestVersion": "review-investigation-promotion-request.v3",
  "producerReleaseId": "reviewrouter-action.2026-08-03",
  "profile": {
    "id": "production",
    "version": "2026-08.v1"
  }
}
```

The operator endpoint still belongs to the operator API v1 surface, but promotion
request v3 is mandatory. A request without the exact request version is rejected
with `promotion_request_version_unsupported`. V2 bodies and any caller-supplied
trust or threshold fields are rejected.

## Required measurements

Every sample declares one exact evidence-completeness class:

- `terminal_operational` is collected automatically from a concluded durable
  investigation. It is observable in total/incomplete counts but is never
  promotion evidence.
- `fully_evaluated` has external ground truth and security disposition and is
  the only class used by promotion gates. In production it is derived only from
  an accepted signed evaluation attestation; the original terminal sample stays
  immutable.

- seeded and shadow sample counts;
- expected and detected defects;
- false verified-clean count;
- unexplained disagreement count;
- security violation count;
- exact and cross-revision replay hits;
- p50/p95 total tokens, completion latency, and capacity wait;
- provider, actual model, turns, critic cycles, gateway operations, and retained
  or protocol bytes in the underlying sanitized samples.

Provider-reported token usage is preferred. Estimated values must be represented
by a separate measurement source before production promotion; do not mix trusted
and estimated values under one label. Missing measurements are `null`, never
synthetic zero. Percentiles are `null` when no fully evaluated sample supplies
the measurement.

## Hard blockers

- any false verified clean;
- any missed seeded defect;
- any security/privacy violation;
- insufficient seeded or shadow samples;
- unexplained disagreements above the approved budget;
- p95 token or latency above the approved budget.

## Current local evidence

The current operations tests feed synthetic, fully evaluated telemetry samples
named after hidden-caller, shared-schema, delete/invalidation, and auth/policy
scenarios. They prove report generation, blocker evaluation, configured policy
binding, cryptographic rejection of dummy signatures, and adversarial rejection
of mixed, stale, missing, and tampered attestations. A deterministic concurrency
test proves that evaluation import waits for report save on the shared release
lock. A database-gated test proves the real Prisma transaction and exact trust
profile read, including mismatch and expiry rejection. These tests do not execute seeded defects through
a Git repository, gateway, agent, and full API lifecycle, do not count as the
disposable seeded corpus or production shadow evidence, and do not authorize a
rollout.
